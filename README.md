# AML: граф внутрибанковских переводов

Локальный воспроизводимый анализ июля 2026: Python, pandas, NetworkX; без облака, GPU, внешних данных и CDN. Роли — гипотезы для проверки потоков, не утверждения о виновности. Исходные данные и starter не изменяются.

## Запуск одной командой

Из корня проекта, Python 3.11 или 3.12:

```bash
sh run.sh
```

Скрипт создаёт `.venv`, устанавливает закреплённые зависимости и выполняет весь расчёт. Интернет нужен только для первоначальной установки пакетов. Уже подготовленное окружение запускается полностью офлайн:

```bash
.venv/bin/python run_pipeline.py
```

При активированном окружении достаточно `python run_pipeline.py`. Пути по умолчанию привязаны к расположению скрипта, а не к текущей директории. Параметры: `--data data --out output --top 30` (top ≥20). Повторный запуск заменяет производные файлы в output. Хеши CSV при одинаковых входах и версиях совпадают; время в отчёте может меняться.

Для просмотра откройте `output/graph.html` обычным браузером двойным кликом: файл автономный, данные встроены. Альтернатива:

```bash
.venv/bin/python -m http.server 8765 --bind 127.0.0.1
```

Адрес: http://127.0.0.1:8765/output/graph.html. Поиск точного gid, выбор кластера, цвет роли, стрелки платежей, масштабирование, перемещение, режим соседей. Нажатие на узел показывает evidence, суммы, временные признаки и все входящие/исходящие связи; на соседей можно переходить. Seed имеют белую обводку. Компоновка условная, группирует сообщества; геометрическое расстояние не интерпретируется как финансовая близость.

## Структура

- `pipeline/load.py`: схема, типы, NULL, уникальность gid/пар, диапазоны, концы рёбер, даты, порог, сверка сумм и числа транзакций.
- `pipeline/metrics.py`: направленный граф со всеми узлами, метрики и BFS от seed.
- `pipeline/roles.py`: последовательные правила ролей и объяснения.
- `pipeline/clustering.py`: Louvain по компонентам и сводки.
- `pipeline/ranking.py`: приоритет, его слагаемые и топ-лист.
- `run_pipeline.py`: единая точка входа, контроль контрактов и все выгрузки.
- `app/build.py`, `app/template.html`: автономный Canvas-интерфейс без сторонних JS-библиотек.
- `tests/test_pipeline.py`: граничные случаи, направление времени, изоляты, повреждение агрегатов и выходной контракт.

## Метрики

`in_degree=fan_in` и `out_degree=fan_out` — число уникальных плательщиков и получателей. `sum_in`, `sum_out` — суммы по направлению; `n_tx_in`, `n_tx_out` — число переводов. `volume=sum_in+sum_out` — интенсивность участия узла: проходящая через узел сумма может учитываться дважды, это не остаток на счёте.

`pass_through_ratio=sum_out/sum_in` только при положительном входе, иначе NULL и `zero_sum_in=True`. Неопределённость сохраняется в метриках, а не заменяется нулём. `is_depth4_leaf=(depth==4 and out_degree==0)`. Изоляты сохраняются, получают нулевые степени и NULL дат.

`first_tx`, `last_tx`, `activity_span_hours` — первая/последняя дата любого входящего или исходящего перевода и интервал между ними; это окно наблюдаемой активности, не время удержания денег. `rapid_out_share` — доля исходящей суммы, для которой есть хотя бы один входящий перевод не позднее выхода и не более чем за 24 часа. Поиск ближайшего предыдущего входа через бинарный поиск. Суммы не сопоставляются, один вход может сопровождать несколько выходов: признак характеризует лишь временное соседство.

В текущем датасете даты имеют точность до дня. «0..24 часа» фактически означает тот же или следующий календарный день; порядок переводов внутри дня неизвестен. Поэтому даже при высоком признаке нельзя считать быстрый транзит доказанным.

`seed_hops` — кратчайший направленный путь от любого seed, рассчитанный общим BFS, 0 для seed и -1 для недостижимого узла. Это самостоятельный признак, а не слепое копирование depth.

## Критерии и пороги ролей

Правила проверяются сверху вниз; срабатывает только первое. Числа — исследовательские эвристики без подгонки под конкретные gid. `role_score` — условная сила правила, не откалиброванная вероятность.

| Порядок / роль | Условие | Базовый score |
|---|---|---|
| 1. coordinator | fan_in ≥5, fan_out ≥5, volume ≥90-го перцентиля всех узлов | 0,85 |
| 2. terminal на границе | is_depth4_leaf и sum_in >0, независимо от fan_in | 0,25 |
| 3. consolidator | не seed, fan_in ≥5 и pass_through_ratio ≤0,2 | 0,80 |
| 4. distributor | fan_out ≥5, pass_through_ratio ≥0,8, rapid_out_share ≥0,5 | 0,75 |
| 5. transit | не seed, ratio 0,8–1,2 включительно, обе степени >0, большая ≤2×меньшей, rapid_out_share ≥0,5 | 0,75 |
| 6. terminal внутри выборки | sum_in >0 и fan_out=0 | 0,65 |
| 7. peripheral | остальные, включая изоляты | 0,40 |

Для любого seed score дополнительно ограничен 0,55, evidence сообщает о неполном входе. Seed исключены из правил накопления и сбалансированного транзита; для distributor у seed отношение к входу ненадёжно, поэтому уверенность снижена. Нулевой вход не проходит условия на ratio.

Пять контрагентов отделяют ветвление/сбор от единичной связи: на этих данных медианы fan_in/fan_out равны 1/0, 95-е перцентили — 3/5. Порог 20% означает, что в наблюдаемом графе дальше ушло не более пятой части входа. Диапазон 0,8–1,2 допускает 20% дисбаланса; фактор 2 ограничивает асимметрию числа связей. Порог временной доли 50% требует поддержки хотя бы половиной исходящей суммы. P90 выделяет верхнюю десятую часть узлов по объёму, адаптируясь к масштабу сумм: в текущем запуске **741 811,70 KZT**. Точные параметры сохранены в отчёте.

Граница проверяется до накопления: даже большой fan_in на глубине 4 не превращает обрыв графа в доказанную консолидацию. Evidence таких terminal содержит точную оговорку «возможен артефакт обрыва графа на 4 колене». Для остальных terminal отсутствие выхода означает отсутствие выхода в этой выборке; настоящий конечный получатель также требует проверки полных выписок. Peripheral означает отсутствие сработавшего правила, а не подтверждённую безопасность.

## Кластеризация

Взвешенный Louvain NetworkX, `resolution=1`, `seed=42`. В неориентированной проекции встречные суммы складываются, не затираются. Направления сохраняются во всех остальных расчётах и визуализации. Алгоритм запускается отдельно внутри каждой слабосвязной компоненты; одиночные узлы получают собственное сообщество. Кластеры нумеруются с нуля в порядке минимального gid; этот порядок стабилен при повторе, но номера могут меняться при изменении входов. Модульность выделяет сообщества связанных переводов, а не юридические группы.

`sum_kzt_internal` складывает исходные направленные рёбра внутри сообщества ровно по одному разу. `top_gids` — JSON-массив до пяти gid по приоритету с разрешением равенств по gid. Гипотезы описывают размер, количество seed и роль приоритетного участника, не приписывая кластеру преступную деятельность.

## Priority score

```text
0,40 × вес_роли × role_score
+ 0,25 × log1p(volume) / max(log1p(volume))
+ 0,20 × log1p(fan_in+fan_out) / max(log1p(fan_in+fan_out))
+ 0,15 × 1/(1+seed_hops)
```

При нулевом максимуме нормированное слагаемое равно 0; для недостижимых от seed близость 0. Веса ролей: coordinator 1; consolidator 0,95; distributor 0,75; transit 0,65; terminal 0,45; peripheral 0,10. Логарифм сдерживает влияние крупнейших сумм, score границы снижает вклад недостоверной роли. Слагаемые вместе не превышают 1. Эти веса выражают приоритет ручной проверки, не вероятность нарушения. В `why` приведены все вклады, хопы, количество транзакций и evidence. Сортировка score по убыванию, при равенстве gid по возрастанию. Абсолютные scores между разными выборками напрямую несопоставимы из-за нормирования.

## Выходные файлы

Три CSV имеют **строго** следующие столбцы, без дополнительных; код проверяет заполненность и диапазоны:

| Файл | Схема |
|---|---|
| `output/nodes_roles.csv` | gid, role, role_score, cluster_id, priority_score, evidence |
| `output/clusters.csv` | cluster_id, n_nodes, n_seed, sum_kzt_internal, top_gids, hypothesis |
| `output/top_nodes.csv` | rank, gid, role, priority_score, why |

CSV в UTF-8 с заголовками, запятая-разделитель, стандартное quoting; evidence 1–200 символов. Все 2248 узлов включены; top по умолчанию 30.

Дополнительно: `node_metrics.parquet` содержит все рассчитанные метрики, роли и слагаемые приоритета; неопределённые ratio/даты остаются NULL. `run_report.json` содержит фактические размеры, распределение ролей, пороги и время. `graph.html` содержит весь граф и работает без сервера. Эти файлы содержат исходные gid и суммы и предназначены для локального просмотра.

## Проверка на предоставленных данных

Полный расчёт с созданием HTML: около **3,76 с** внутри точки входа при первом проверенном запуске; установка зависимостей не входит в время пересчёта. 2248 узлов, 3119 рёбер, 4840 транзакций, 81 seed; 105 сообществ. Роли: terminal 1527 (из них 444 — обрыв глубины 4), peripheral 634, transit 32, consolidator 19, coordinator 18, distributor 18.

Существенное уточнение: **16 компонент с рёбрами**, минимальная — 2 узла, плюс **19 изолированных узлов** из nodes.parquet. Поэтому полный граф имеет **35 компонент**, а не 16. Изоляты не удалены и не искусственно объединены.

```bash
.venv/bin/python -m unittest discover -s tests -v
```

Дополнительно выполнен smoke-тест в локальном headless Chrome: отрисовка, выбор узла, поиск существующего/неизвестного gid, режим соседей и сброс. Ошибок JavaScript не обнаружено. Повторный расчёт занял 0,46 с; SHA-256 всех трёх CSV совпал с предыдущим запуском.

Тесты проверяют артефакт границы с высоким fan_in, исключение seed из консолидации, сохранение изолятов, запрет временного сопоставления с будущим входом, приём 24-часовой границы, отклонение неверного n_tx и контракт реальной выгрузки. При каждом запуске также проверяются суммы транзакций против рёбер, заполненность CSV, длины evidence, диапазоны scores и отсутствие объединения компонент.

## Ограничения

- Обход только исходящий, до 4 колен: отсутствие дальнейшего перевода не доказывает оседание. Граница отмечена явно, уверенность снижена.
- Вход seed и других узлов может быть занижен из-за отбора; sum_in=0 не означает отсутствие средств. Отношение сумм не является балансом банковского счёта.
- Сделки <5000 KZT, переводы в другие банки и за пределами июля отсутствуют; временные цепочки могут начинаться раньше и продолжаться позже периода.
- Учитываются 16 компонент с рёбрами и 19 изолятов. Их сообщества не объединяются искусственно.
- Нет ground truth, клиентских атрибутов, назначения платежа и начальных остатков. Точность/полнота выявления не оценивались, scores не калиброваны.
- Дневная точность дат и простое временное соседство не доказывают движение тех же денег. Сообщества, роли и приоритет требуют экспертной проверки.
- Пороги эвристические: полезно проверить устойчивость при fan=3/5/10, ratio=0,1/0,2/0,3 и разных resolution до операционного использования.

## Масштабирование до ~1 млн узлов

Чтение и валидацию перенести на DuckDB/Polars с проекцией колонок, агрегацией и партиционированным Parquet; транзакции обрабатывать пакетами, отсортированными по gid и времени. Хранить gid как int64 и компактно перенумеровать их для CSR-графа. pandas/NetworkX с Python-объектами заменить на igraph либо другую реализацию графовых алгоритмов на C/C++: сумма степеней, BFS и агрегации линейны по рёбрам, но объекты NetworkX расходуют много памяти. Временной признак считать merge/as-of или потоковым проходом по отсортированным событиям, избегая копирования всех групп.

Louvain/Leiden выполнять по компонентам на CPU с контролем памяти, фиксированным seed и версионированием конфигурации; крупнейшую компоненту обрабатывать специализированным движком. Порог P90 вычислять точно в движке колонок или приближённо с указанной погрешностью. Обновления метрик и ролей делать инкрементально, сообщества пересчитывать по расписанию и отслеживать изменение их состава.

Не встраивать миллион узлов в HTML: API для поиска gid, агрегированная карта сообществ, загрузка ego-графов с ограничением размера, WebGL для видимого подграфа. Сохранить отдельно компактные итоговые таблицы и аудиторские метрики, вести манифест входов, версии, время и тесты качества. Требование 5 минут для текущей выборки не переносится автоматически на миллион узлов: нужен замер числа рёбер, памяти и распределения размеров компонент.

## Карточка дела и запросы недостающих данных

Выберите узел и нажмите **«Открыть карточку дела»** либо **«Каких данных не хватает?»**. В карточке показаны evidence с фактическими метриками, транзакции узла, связанные seed и по одному кратчайшему направленному пути от каждого достижимого seed. Цепочки строятся BFS без хардкода gid; временная последовательность пути не проверяется. Путь в месячном графе не доказывает движение одной суммы. Для самого seed отображается путь нулевой длины.

Статусы: «Новое», «Проверяется», «Закрыто», «Эскалировано». Кнопка «Сохранить решение» сохраняет статус и комментарий, добавляя время, предыдущий и новый статус и текст основания в историю. Для закрытия/эскалации комментарий обязателен. При выходе с несохранёнными изменениями появляется предупреждение.

Хранение — `localStorage` текущего браузера, с ключом из SHA-256 входной выборки и gid. После перезагрузки записи сохраняются; другой браузер/адрес, очистка хранилища или изменение входной выборки дают отдельное состояние. Для file:// поддержка хранилища зависит от браузера; предпочтителен локальный HTTP-сервер. При ошибке хранения интерфейс сообщает о ней. Это прототип персональной работы, без авторизации, совместного редактирования и защищённого аудита; дата истории берётся с локальных часов. Очистка браузера удалит историю — экспортируйте нужные дела. JSON-импорт не реализован.

Экспорт:

- **Справка HTML** — автономный документ: факты, роль, комментарий, ограничения, пути, запросы, история и операции; можно распечатать в PDF средствами браузера. Не является регуляторным сообщением ФМ-1.
- **Дело JSON** — структурированная копия метрик, транзакций, контекста, решения и истории с отпечатком данных. Несохранённые изменения явно помечены как черновик.
- **Список запросов TXT** — конкретные запросы с основаниями, gid и отпечатком выборки.

Транзакции имеют ссылку `row:N` на позицию в исходном transactions.parquet (нумерация с 1). Это не банковский идентификатор: одинаковые строки не удаляются и остаются отдельными наблюдениями. Все gid в браузере и экспорте JSON — строки для сохранения точности int64.

Запросы формируются прозрачными условиями в `app/cases.py`:

| Наблюдение | Рекомендованный запрос |
|---|---|
| depth4 leaf | Дальнейшие исходящие переводы, расширение обхода |
| seed, нулевой вход или ratio >1,2 | Полный входящий поток и начальный остаток |
| Есть вход и выход | Точное время, часовой пояс, порядок операций |
| Вход больше выхода | При разрешённом доступе — межбанковские переводы, снятия и другие способы вывода |
| Нет входящих и исходящих связей | Проверка полноты выгрузки и фильтров |
| Для всех | Расширение периода, операции ниже 5000 KZT, полнота каналов |

Приложение лишь формирует запросы для аналитика: внешние данные не запрашиваются и не добавляются. Дополнительные тесты проверяют направление путей, циклы, недостижимые узлы и условия запросов. В Chrome проверены обязательность основания, сохранение после перезагрузки, история и HTML/JSON-экспорт, включая безопасное отображение специального текста комментария.
